# glue_details — Enriquecedor de Detalhes

## O que é

O Glue Details é o terceiro estágio do pipeline de dados. Acionado pelo Glue ETL após cada tabela `discover` ser processada, ele busca na API do TMDB informações complementares para cada filme ou série: duração, número de temporadas/episódios, plataformas de streaming disponíveis no Brasil, elenco (top 5 atores), diretor, roteiristas, compositor da trilha sonora, produtor(es), diretor de fotografia, montador(a), país de origem (filmes), países de produção, keywords temáticas, classificação indicativa BR, data de estreia teatral BR (filmes, `theatrical_release_date_br` — extraída do mesmo `release_dates` da certificação, priorizando `type=3` "Theatrical" e usando `type=2` "Theatrical limited" como fallback), trailer, coleção/franquia, produtoras, status, tagline, IMDB ID, títulos recomendados, títulos similares, títulos alternativos/regionais e, para séries, o próximo episódio agendado (`next_episode_air_date`/`next_episode_number`/`next_episode_season_number`/`next_episode_name`) e o histórico/anúncio de temporadas (`season_numbers`/`season_air_dates`/`season_episode_counts`/`season_names`). Também obtém traduções pt-BR de sinopses e taglines diretamente do TMDB (via `append_to_response=translations`) e, quando não disponíveis, traduz para o português via **LLM** (OpenRouter, `litellm` — ver `shared_utils.traducao_llm`), com fallback nativo de modelo embutido na própria chamada. Keywords são sempre traduzidas (o TMDB não as localiza), pelo mesmo serviço. Antes de qualquer tradução, detecta o idioma do texto fonte (`overview_en`/`tagline`/`keywords`) via LLM (`shared_utils.idioma_llm`), gravando `<campo>_detected_language_en`; quando a fonte já é detectada como `pt`, copia direto para `<campo>_pt` sem chamar o LLM (evita retradução infinita de texto que já está correto). O idioma do **resultado** também é detectado e gravado em `<campo>_detected_language_pt` — é esse idioma (não uma comparação de string com a fonte) que decide se o campo ainda precisa de tradução, o que evita tanto retraduzir o que já está correto quanto deixar uma mistradução silenciosa marcada como concluída para sempre. `<campo>_translation_attempts` conta quantas vezes uma linha foi reenviada ao tradutor, para não retentar para sempre conteúdo genuinamente não traduzível (nomes próprios, termos curtos). Grava os resultados em tabelas separadas na camada SOT.

## Por que existe

A API de discover do TMDB retorna metadados básicos (título, nota, gênero). Informações como duração de filmes, número de temporadas de séries, elenco, diretor, produtor, diretor de fotografia, montador, keywords temáticas, classificação indicativa, títulos recomendados/similares/alternativos e onde assistir no Brasil requerem endpoints específicos por ID. Este job faz esse enriquecimento de forma eficiente em paralelo, usando o parâmetro `append_to_response` para obter credits, keywords, release_dates/content_ratings, videos, external_ids, recommendations, similar, alternative_titles e translations na mesma chamada de API (sem custo adicional de rate limit).

## Como funciona

1. Lê os argumentos do job (media_type, year, end_year, databases, nomes dos buckets e jobs)
2. Busca a chave da API TMDB no Secrets Manager (cofre de senhas da AWS)
3. Consulta o Athena para obter a lista de todos os IDs únicos da tabela `discover` para o ano especificado
4. **Sem delta — busca sempre todos os IDs do discover do ano:** a cada execução, o job busca/atualiza os detalhes de **todos** os IDs retornados pelo discover para o `year`/`media_type`, sem calcular um delta contra o que já foi processado. Isso mantém o dado sempre atualizado (sem uma janela de staleness de até 1 mês esperando a virada de calendário), ao custo de mais chamadas à API TMDB em execuções mais frequentes (ex.: o ano corrente roda ~4x/mês, então passa a rebuscar tudo a cada execução, não só na primeira do mês)
5. Para cada ID do discover, chama `/movie/{id}` ou `/tv/{id}` (via `ThreadPoolExecutor`) e grava em `tb_tmdb_details_{movie|tv}_{env}`. Registros sem `release_date`/`first_air_date` ficam sem `year` e são descartados antes da gravação — se **todos** os registros do lote ficarem sem `year`, nada é gravado neste run (evita erro de partição vazia no S3). Antes de traduzir, lê uma única vez (por partição `year` afetada) os registros já existentes no S3 — não o mesmo mecanismo do passo 4 (removido), mas um merge interno de `collect_and_write_details`: como o `release_date` de um ID pode cair num `year` diferente do `year` do discover que o trouxe, IDs já existentes numa partição `year` que **não** fazem parte do batch atual são preservados para o merge final de escrita; os que **fazem** parte do batch atual (serão sobrescritos) alimentam o cache de tradução do passo 6 (mesma leitura reaproveitada para as duas finalidades, sem consultar o S3 duas vezes)
6. **Tradução de sinopses (TMDB pt-BR → cache do S3 → idioma detectado → cópia direta ou LLM):** verifica primeiro se o TMDB já possui tradução pt-BR (extraída do `append_to_response=translations`); caso exista, usa diretamente. Caso contrário, verifica se `overview_en` é idêntico ao registro existente lido do S3 (ver passo 5) — se for, reaproveita `overview_pt` já persistido sem chamar a API de tradução de novo — e, junto, `overview_detected_language_en`/`overview_detected_language_pt` já persistidos quando o texto correspondente é idêntico (`reuse_detected_language`), poupando a redetecção por LLM; só o que mudou ou ainda não tinha idioma detectado vai ao LLM. A partir daí, `resolve_pt_translation` (`shared_utils.traducao`) assume o resto do fluxo: detecta o idioma de `overview_en` (grava `overview_detected_language_en`) e do valor atual de `overview_pt` (grava `overview_detected_language_pt`), copia `overview_en` direto para `overview_pt` quando a fonte já é `"pt"` e `overview_pt` ainda está vazia (sem chamar tradução), e traduz via `translate_text_llm` (`shared_utils.traducao_llm`, OpenRouter/`litellm`, com fallback nativo de modelo) — todo registro com `overview_en` preenchido cujo `overview_detected_language_pt` ainda não seja `"pt"` e que não tenha esgotado `overview_translation_attempts`, e cujo idioma do destino tenha sido detectado (se a detecção do `overview_pt` atual falhou, ele é mantido como está — nunca sobrescreve uma tradução nativa do TMDB — e a detecção é refeita na próxima execução; `overview_needs_translation` fica `True` enquanto isso) (teto contra retry infinito de conteúdo genuinamente não traduzível, relevante também porque o LLM não é determinístico). `original_language` não entra em nenhum critério — é o idioma de produção original do título, não o idioma do texto retornado pela API, e não garante que `overview_en` já esteja em português (ver `shared_utils/traducao.py`). Também grava `overview_needs_translation` (booleano): `overview_en` preenchido E `overview_detected_language_pt != "pt"` E `overview_pt` não alterado em relação a `overview_en` (se o texto mudou, foi traduzido, e a dúvida do detector em textos curtos não reabre a pendência), sem o teto de tentativas — ao contrário do critério de elegibilidade acima, continua `True` mesmo depois de `overview_translation_attempts` esgotar. Hoje nenhum consumidor lê essa coluna (é diagnóstico/auditoria; o FilmBot e o Glue AGG não a usam); as colunas `keywords_needs_translation` e `tagline_needs_translation` seguem a mesma definição.6b. **Tradução de keywords (cache do S3 → idioma detectado → cópia direta ou LLM):** mesmo fluxo do item 6 via `resolve_pt_translation`, aplicado a `keywords` (grava `keywords_detected_language_en`/`keywords_detected_language_pt`/`keywords_translation_attempts`/`keywords_needs_translation`), sem tradução nativa do TMDB (o TMDB não localiza keywords por idioma — nem mesmo para títulos com `original_language == 'pt'`), gravando na coluna `keywords_pt`
6c. **Tradução de tagline (TMDB pt-BR → cache do S3 → idioma detectado → cópia direta ou LLM):** mesmo fluxo do item 6 (incluindo a prioridade de tradução nativa do TMDB), aplicado a `tagline` (grava `tagline_detected_language_en`/`tagline_detected_language_pt`/`tagline_translation_attempts`/`tagline_needs_translation`), gravando na coluna `tagline_pt`
6d. **Países de produção:** extrai os códigos ISO 3166-1 dos países de produção (`production_countries_iso`) para lookup na tabela de referência `tb_configuration_countries` no Glue AGG6e2. **Idiomas falados:** extrai os códigos ISO 639-1 dos idiomas falados (`spoken_languages_iso`) para lookup na tabela de referência `tb_configuration_languages` no Glue AGG, resolvendo nomes em português
6e. **Coleções em pt-BR:** para filmes com coleção/franquia, busca o nome em português via `/collection/{id}?language=pt-BR` na API do TMDB. Chamadas deduplicadas por collection_id (1 chamada para toda a coleção, ex: Marvel = 1 chamada para 30+ filmes). Grava na coluna `collection_name_pt`
7. **Watch providers — sem delta, mesma lista de IDs do discover:** para cada ID do discover, chama `/movie/{id}/watch/providers` ou `/tv/{id}/watch/providers` e grava em `tb_tmdb_watch_providers_{movie|tv}_{env}`
8. Aciona o Glue Data Quality para cada tabela gravada
9. **Ao final do ciclo de cada `media_type`** (quando `year == end_year`): executa `repair_discover_duplicates`, `repair_watch_providers_duplicates` e `repair_details_duplicates` para eliminar IDs duplicados na partição do ano corrente. Cada repair lê o Parquet diretamente via S3, aplica `drop_duplicates` e grava de volta apenas se houver mudanças. Movie e TV reparando suas próprias tabelas em runs separados

Chamadas à API usam **retry com backoff exponencial e jitter** para lidar com rate limits do TMDB — se a API retornar erro 429 (muitas requisições), o código espera um tempo crescente entre tentativas (ex: 1s, 2s, 4s…) com uma variação aleatória (jitter) para evitar que múltiplos workers tentem ao mesmo tempo.

### Modo changes (TMDB Changes API)

Acionado pela `lambda_api` (modo `only_changes_tables`, semanal aos sábados) via o argumento opcional `CHANGES_S3_PATH` — um caminho `s3://bucket/key` com a lista de IDs sinalizados pelo `/movie/changes`/`/tv/changes` do TMDB como alterados numa janela de data recente, **independente do ano de lançamento**. Fecha o gap de staleness que os modos semanal/mensal não cobrem (títulos com `year < ano_atual - 1` nunca são re-tocados por eles).

`CHANGES_S3_PATH` pode se originar tanto do lookback semanal automático quanto de um disparo manual sob demanda (`scripts/backfill_changes.py`) — em ambos os casos a janela é sempre `[domingo passado, sábado de ontem]` e o consumo pelo Glue Details é idêntico, sem nenhuma mudança de código aqui (ver `app/lambda_api/lambda_api.md`, seção "Modo changes").

Quando `CHANGES_S3_PATH` está presente, o `main()` entra num ramo antecipado que substitui inteiramente o fluxo `YEAR`/`END_YEAR`:

1. `fetch_ids_from_changes_file()` lê o payload de IDs do S3 (gravado pela `lambda_api`) — retorna o dicionário completo (`ids`, `start_date`, `end_date`, `content_type`), não só a lista de IDs
2. `resolve_matched_ids_for_changed_ids()` cruza os IDs com a tabela discover via Athena para confirmar pertencimento ao catálogo — a tabela discover é a "base existente" do catálogo: IDs que não constam nela nunca cruzaram a régua de popularidade do `/discover` e são **descartados** (este fluxo nunca expande o catálogo). A lista completa de descartados (não só a contagem) é gravada em `s3://{s3_bucket_temp}/tmdb/changes/{content_type}/discarded_{data}.json` para investigação manual futura. **Não resolve o `year`** — a query agrupa por id (`GROUP BY`) só para detectar e logar em `discover_years_ambiguos_{data}.json` os IDs com mais de um `year` distinto entre partições da discover (possível porque `glue_etl` grava discover com `overwrite_partitions`, uma partição `year` por vez); esse log é só para investigação futura da causa raiz, nunca usado para decidir partição
3. **Sinal de tradução por ID (`fetch_translatable_changes_for_ids`), só se `start_date`/`end_date` estiverem disponíveis:** para cada ID confirmado no passo 2, consulta em paralelo `/movie/{id}/changes` ou `/tv/{id}/changes` (diferente de `/movie|tv/changes` — este diz exatamente qual campo mudou por título, com o valor novo) e resolve, via `extract_translatable_changes`, se `overview`/`tagline`/`plot_keywords` (mapeado para `keywords`) tiveram alguma mudança em inglês na janela. Motivo: um ID pode entrar na lista de changes por qualquer motivo (`status`, `runtime`, imagens, etc.) sem que o texto traduzível tenha mudado — sem esse sinal, o passo 4 assumiria que precisa retraduzir mesmo assim. Falha de rede num ID individual não interrompe o lote: esse ID simplesmente fica sem sinal, e o passo 4 decide para ele do jeito de sempre (comparação de string)
4. `process_changed_ids()` orquestra o refresh: chama `collect_and_write_details()` com todos os IDs confirmados e o dicionário do passo 3 (`changed_fields_by_id`, pode ser `None`) — a função já deriva o ano do `release_date`/`first_air_date` de cada resposta e devolve `{id: year}` dos IDs efetivamente buscados. Dentro de `collect_and_write_details`, `_force_reuse_when_unflagged` usa `changed_fields_by_id` para pular a chamada ao LLM num campo quando o `/changes` por ID confirma que ele não mudou — mesmo que o texto reextraído da API divirja byte-a-byte do salvo (ex.: TMDB reordena `keywords` sem mudança real de conteúdo, o que a comparação de string de `reuse_existing_translation` trataria como "mudou"). Depois, agrupa os IDs **pelo `year` retornado pela API** (nunca pelo da discover) para `collect_and_write_watch_providers()` (que exige `year` explícito por partição), e roda `repair_details_duplicates`/`repair_watch_providers_duplicates` por ano afetado ao final — mesma proteção contra corrida de escrita já usada no fluxo normal quando `year == end_year`. IDs que falharam na API ou ficaram sem `release_date`/`first_air_date` não aparecem no retorno de `collect_and_write_details` e por isso não são processados para watch providers neste run (a rede de segurança do refresh mensal cobre esses casos depois). Retorna a lista de anos afetados (única, via as chaves do agrupamento por `year`)
5. Aciona o Glue Data Quality **uma vez por tabela** (`TABLE_DETAILS`/`TABLE_WATCH_PROVIDERS`), passando todos os anos afetados juntos num único argumento `YEAR` separado por vírgula (ex.: `"2020,2021,2023"`) — não um disparo por ano. Um changes-run pode afetar dezenas de anos distintos numa única janela (edição de metadado no TMDB não correlaciona com o ano de lançamento do título); agrupar evita pagar o overhead fixo de startup do Spark do Data Quality uma vez por ano (ver `app/glue_data_quality/glue_data_quality.md`, seção "Múltiplos anos por job run")

Este modo **nunca** escreve na tabela discover (`repair_discover_duplicates` não é chamado).

**Escopo deliberado da checagem por ID:** ela só decide se `overview`/`tagline`/`keywords` precisam de tradução — não muda como o restante do registro é buscado (`fetch_tmdb_details` continua completo, sempre) nem como é gravado (`overwrite_partitions` da linha inteira, sem atualização parcial por campo). Uma atualização seletiva mais ampla (aplicar só os campos que o `/changes` por ID reporta, sem refetch completo) foi considerada e descartada por ora — exigiria reescrever o mecanismo de gravação da tabela; fica registrada como evolução futura, não implementada aqui.

**Limitação conhecida:** a duplicação cross-partition da própria tabela `discover` (mesmo id em duas partições `year` ao mesmo tempo) não é corrigida por este fluxo — apenas deixa de ser um risco de dado aqui, já que o `year` da discover nunca decide partição. O arquivo `discover_years_ambiguos_{data}.json` existe para permitir quantificar a frequência real do problema antes de investir num merge manual em `glue_etl` para a tabela discover.

**Nota:** o piso de `year >= 2000` do rotation refresh/backfill (`app/lambda_api/main.py`) rege apenas o que é buscado via `/discover`. `details`/`watch_providers` podem legitimamente ter `year < 2000` para um id descoberto sob um year mais recente cujo `release_date`/`first_air_date` real a TMDB corrigiu depois — não é dado incorreto, é o `year` real da API prevalecendo sobre o year de descoberta (mesma regra de todo o modo changes).

### Reuso fora do Glue (backfill de enriquecimento)

Os passos 3-9 do fluxo `YEAR`/`END_YEAR` acima (coleta de details/watch providers, disparo do Data Quality, repair de duplicatas) vivem em `run_details_and_watch_providers_for_year()`, não inline em `main.py` — isso permite que `scripts/backfill_enriquecimento.py` rode exatamente essa mesma lógica dentro do processo do backfill (GitHub Actions), sem acionar este job Glue, eliminando o custo de Glue Job do backfill histórico de 2000 até o ano atual. A única parte do job que depende do runtime real do Glue é `get_parameters_glue()` (via `getResolvedOptions`), que não é usada por esse caminho — o script de backfill lê os mesmos parâmetros de variáveis de ambiente. A diferença de comportamento entre os dois chamadores é o parâmetro `trigger_dq`: `main.py` (execução real do job, caminho automático via EventBridge) usa o default `True` e dispara o Data Quality por unidade, como sempre; `scripts/backfill_enriquecimento.py` passa `trigger_dq=False` e dispara o Data Quality uma única vez ao final de todo o backfill, cobrindo o range completo de anos (ver `scripts/scripts.md`).

### Reuso fora do Glue (backfill de changes)

Mesmo racional acima, aplicado ao ramo `if changes_s3_path:` (linhas 52-81) em vez do fluxo `YEAR`/`END_YEAR`: `scripts/backfill_changes.py` chama diretamente `fetch_ids_from_changes_file()` e `process_changed_ids()` (ambas 100% Python puro, sem dependência de `getResolvedOptions`) dentro do processo do backfill, sem acionar este job Glue. Diferença em relação ao caso do enriquecimento: aqui há um hop de infraestrutura a mais para bypassar — o script também substitui a invocação da Lambda API (`only_changes_tables=True`) que hoje coleta os IDs mudados, chamando `collect_changes_data()` (`app/lambda_api/src/utils.py`, também Python puro) diretamente. O resultado final é o mesmo: uma lista de IDs mudados gravada em `s3://{s3_bucket_temp}/tmdb/changes/{content_type}/{data}.json`, seguida do mesmo enriquecimento via `process_changed_ids()`. O disparo do Data Quality segue o mesmo padrão de `backfill_enriquecimento.py`: não por ano (já que `process_changed_ids` agrupa os anos afetados por `content_type` num único `YEAR`), e adiado para depois de processar `movie` e `tv` — só dispara (uma vez por tabela, 4 no total) se nenhum dos dois falhou (ver `scripts/scripts.md`).

## Entradas e saídas

| | Descrição |
|---|---|
| **Entrada** | Argumentos: `MEDIA_TYPE`, `YEAR`/`END_YEAR` (opcionais — ausentes no modo changes), `DATABASE`, nomes dos buckets e jobs, `TMDB_SECRET_ARN` (secret unificado — também publicado em `os.environ["FILMBOT_SECRET_ARN"]` dentro de `get_parameters_glue()`, para que `shared_utils.llm_client.load_llm_api_key` leia o campo `llm_api_key` como se fosse o ambiente real), `CHANGES_S3_PATH` (opcional — presente apenas no modo changes, ver seção acima) |
| **Leitura** | Athena (IDs da tabela discover na SOT), Secrets Manager (chave API), API TMDB (inclui `/movie|tv/{id}/changes` por ID no modo changes, ver seção acima); S3 TEMP (payload de changes — IDs + janela, modo changes) |
| **Escrita** | S3 SOT — tabelas `tb_details_*` e `tb_watch_providers_*` como Parquet + Glue Catalog; S3 TEMP — `tmdb/changes/{content_type}/discarded_{data}.json` (IDs descartados no modo changes) e `tmdb/changes/{content_type}/discover_years_ambiguos_{data}.json` (IDs com mais de um `year` na discover, modo changes) |
| **Aciona** | Glue Data Quality (por tabela gravada; no modo changes, uma vez por tabela com todos os anos afetados agrupados em `YEAR`) |

O Glue AGG **não** é mais acionado por este job — roda em agendamento próprio (`aws_glue_trigger` nativo do Glue, sábado e domingo às 08:00 BRT, ver `app/glue_agg/glue_agg.md`), independente do ciclo do Glue Details.

| `collect_and_write_details(ids, ..., changed_fields_by_id=None)` | Faz chamadas paralelas e grava tabela de detalhes. Antes de traduzir, lê o S3 uma única vez por partição `year` afetada, separando os registros existentes em `df_existing_delta` (ids do delta atual, usados como cache de tradução) e `df_existing_keep` (ids fora do delta, preservados no merge final) — a mesma leitura alimenta as duas finalidades. Loga o andamento em 4 etapas (`[Detalhes {movie|tv} 1/4]` coleta na API do TMDB, `2/4` leitura dos registros existentes, `3/4` tradução de overview/keywords/tagline, `4/4` gravação no SOT, com o tempo acumulado em `format_elapsed`), para dar para acompanhar em que parte o job está. A etapa 3/4 roda dentro de `llm_usage_scope()` e fecha com `LLM [<rótulo>]: N chamada(s) (tradução x, detecção y) | modelos: … | tokens a in / b out | US$ …` (+ `sem mudança N` quando o LLM devolveu o próprio texto) e, havendo falhas, uma linha WARNING `LLM [<rótulo>] falhas: N de M — <Exceção> n (ex.: '<texto>': <mensagem>)` — além de uma linha `Balanço '<campo>_pt'` por campo (overview/keywords/tagline, com ids de exemplo das pendentes). `main()` loga o total do job (`LLM [Glue Details — total]`) e o balanço acumulado (`shared_utils.llm_metrics`). Passa `translate_text_llm`/`detect_language_llm` e o teto de workers (`_TRANSLATE_MAX_WORKERS_LLM` — chamadas de LLM são bem mais lentas que uma API de tradução estruturada; valor inicial conservador) uma vez por execução, junto com `df_existing_delta` e `changed_fields_by_id` (só informado no modo changes), às 3 `_add_translations_*`. Retorna `{id: year}` dos IDs efetivamente buscados e gravados nesta execução (year derivado do `release_date`/`first_air_date` da resposta da API) — fonte de year usada por `process_changed_ids` no modo changes |

| `run_details_and_watch_providers_for_year(*, api_key, database, media_type, year, end_year, ..., trigger_dq=True)` | Orquestra o ciclo completo details+watch_providers para um `media_type`/`year`: busca todos os IDs do discover do ano, chama `collect_and_write_details`/`collect_and_write_watch_providers`, dispara o Data Quality (se `trigger_dq`) e repara duplicatas quando `year == end_year`. Chamada por `main.py` (`trigger_dq=True`, padrão) e por `scripts/backfill_enriquecimento.py` (`trigger_dq=False`, fora do runtime do Glue — ver "Reuso fora do Glue" acima) |

| `repair_watch_providers_duplicates(...)` | Lê a partição `year` via S3, aplica `drop_duplicates(id, provider_type, provider_id)` mantendo o `processed_date` mais recente e regrava apenas se houver mudanças |

| `fetch_tmdb_id_changes(api_key, content_type, item_id, start_date, end_date, max_pages=10)` | Chama `/movie/{id}/changes` ou `/tv/{id}/changes` — diferente de `/movie|tv/changes`, diz exatamente quais campos (`key`) mudaram nesse título, com o valor novo para vários tipos. Só busca a página seguinte quando a resposta confirma `total_pages` maior que a atual (a doc oficial não garante esse campo aqui); sem ele, aceita a página 1 como única — decisão deliberada após um incidente real em que confirmar página vazia com uma 2ª chamada dobrava o custo desta consulta para quase todo ID e ela sozinha consumiu 66% do timeout do job (ver `especialista-api-tmdb`) |

|---|---|---|
| `api_get(url, params, max_retries)` | `shared_utils.api_client` | GET com retry/backoff para lidar com rate limits de APIs |

| `trigger_glue_job(job_name, **arguments)` | `shared_utils.triggers` | Dispara qualquer job Glue (usado aqui só para o Data Quality) com argumentos dinâmicos |
| `translate_text_llm(text)` | `shared_utils.traducao_llm` | Traduz texto para PT via LLM (OpenRouter, `litellm`), com fallback nativo de modelo; retorna o texto original em caso de falha |
| `translate_in_parallel(values, translate_fn, max_workers, progress_label=None)` | `shared_utils.traducao` | Aplica `translate_fn` a cada valor em paralelo via `ThreadPoolExecutor`, com log de progresso a cada 10% em lotes grandes; usada por `resolve_pt_translation` e `detect_in_parallel` |
| `detect_in_parallel(texts, detect_fn, max_workers, label)` | `shared_utils.traducao` | Detecção de idioma em paralelo, com progresso e resumo de falhas; usada por `resolve_pt_translation` para a fonte, o destino e a redetecção dos recém-traduzidos (antes eram `.apply` em série — 2 detecções por campo e por registro) |
| `resolve_pt_translation(df, source_column, target_column, detected_language_en_column, detected_language_pt_column, translation_attempts_column, detect_fn, translate_fn, max_workers, max_attempts, needs_translation_column=None)` | `shared_utils.traducao` | Detecta o idioma da fonte e do resultado (só onde ainda vazios, em paralelo), copia a fonte direto quando ela já é `"pt"`, traduz as linhas elegíveis (fonte preenchida, idioma do resultado ainda diferente de `"pt"`, tentativas abaixo do teto, idioma do destino disponível — detecção nula num destino com texto mantém a linha como está), incrementa o contador de tentativas e redetecta o idioma do resultado só nas linhas recém-traduzidas. Com `needs_translation_column` informado (usado pelos 3 campos deste job), grava também um booleano de "ainda não está em português" (idioma do destino ≠ `"pt"` e texto não alterado em relação à fonte) sem o teto de tentativas. Devolve `(df, quantidade traduzida com sucesso)`. Compartilhada com `scripts/backfill_traducao.py` e `glue_etl` para evitar que as cópias divirjam |
| `reuse_existing_translation(df, previous_df, source_column, target_column, key_column="id", detected_language_en_column=None, detected_language_pt_column=None)` | `shared_utils.traducao` | Pré-preenche `target_column` do `df` novo com o valor já persistido (`previous_df`) quando `source_column` não mudou para o mesmo `key_column`; as 3 `_add_translations_*` passam as colunas `*_detected_language_en`/`*_detected_language_pt`, para também reaproveitar o idioma já detectado (`reuse_detected_language`). Não sobrescreve valor já preenchido (prioridade da tradução nativa do TMDB); registros novos sem histórico ou schema antigo sem a coluna não são afetados. Compartilhada com `glue_etl` (que usa `key_column="iso_3166_1"`/`"iso_639_1"` para a tabela `configuration`) |
| `detect_language_llm(text)` | `shared_utils.idioma_llm` | Detecção de idioma via LLM (OpenRouter), devolvendo o código ISO 639-1 ou `None` — nunca lança exceção |
| `get_resolved_option(args)` | `shared_utils.glue_helpers` | Wrapper de `getResolvedOptions` — converte lista de nomes de argumentos em dicionário nome→valor |
| `configure_glue_logging()` | `shared_utils.glue_helpers` | Configura o logging padrão dos jobs Glue (stdout, nível INFO, formato com timestamp) |

## Tecnologias

- **requests** + **ThreadPoolExecutor** — chamadas paralelas à API com controle de concorrência
- **litellm** (OpenRouter) — tradução e detecção de idioma via LLM para sinopses, keywords e taglines quando a tradução pt-BR não existe no TMDB; chave lida do secret unificado (`FILMBOT_SECRET_ARN`/`llm_api_key`), sem custo de API key própria do job; o `tenacity` também fica em `requirements.txt` porque o `litellm` só o importa ao retentar (`num_retries`) e não o declara — sem ele, todo erro transitório (429/timeout) vira falha na hora
- **awswrangler** — consultas Athena e escrita Parquet
- **boto3** — Secrets Manager e acionamento de jobs Glue
